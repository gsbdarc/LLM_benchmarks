## Context / why

This repo benchmarks LLMs. The **metric-calculation** step is being converted from
deterministic code (`scripts/6b_mongo_eval.py` + `scripts/evaluator.py`) into an **agentic
MCP workflow** (`mcp/`), with an observability **dashboard**. A hand-authored mockup
(`mcp/agent_dashboard_sample_v2.html`, all fake/hardcoded numbers) is the visual target. It
was shown to the team; this plan folds their feedback in and wires real data.

**Working mode:** mockup-first. Update the mockup (fake data is fine) to reflect every
decision so the team can sign off, then make the upstream changes that populate it, then
port the mockup design into the real generator.

## Current architecture (facts you need)

- **Deterministic baseline:** `scripts/6b_mongo_eval.py` reads MongoDB `llm_outputs`, joins
  ground truth, and calls metric functions in `scripts/evaluator.py`. The benchmark spec
  declares which metric each field uses.
- **7 metric functions** live in `scripts/evaluator.py`: `word_iou`, `null_accuracy`,
  `levenshtein_similarity`, `char_f1`, `set_f1`, `sequence_lcs`, `set_inclusion`.
- **Per-type composite scoring** is inline in `scripts/evaluator.py:399-425`
  (`evaluate_task`):
  - `raw_string` → `word_iou`
  - `extracted_string` → `null_accuracy × max(levenshtein_similarity, char_f1)`
  - `list` → `max(set_f1, sequence_lcs, set_inclusion)`
- **Agentic path (`mcp/`):**
  - `mcp/metric_server.py` — FastMCP HTTP server. 3 data tools (`list_outputs`,
    `get_task_output`, `save_evaluation`) + the 7 metric tools (lines 147-225). Tool
    descriptions deliberately teach the model to classify a field's data shape; the declared
    metric is hidden so the agent must reason.
  - `mcp/metric_tools.py` — MongoDB business logic; imports the 7 metrics from
    `scripts/evaluator.py` (single source of truth).
  - `mcp/eval/` package: `config.py` (backends), `prompts.py` (`PROMPT_NAME`,
    `METRIC_EVAL_SYSTEM`), `agent.py` (async loop, persistent MCP session, retries),
    `observability.py` (Weave + vLLM Prometheus scrape + perf), `integrity.py`
    (`check_score_consistency`), `scorers.py` (Weave scorers incl. `selection_accuracy`),
    `sink.py` (`flatten_run` → one Parquet row per run), `runner.py` (`run_batch` with
    `asyncio.Semaphore`), `__main__.py` (CLI: `python -m agent_eval`).
  - Observability: **Weave** traces (deep, per-run, `weave_trace_url`) + **Parquet/DuckDB**
    (wide, many runs, `outputs/agent_runs/date=YYYY-MM-DD/*.parquet`).
- **Dashboard = generated, not hand-built.** `analysis/build_dashboard.py` injects DuckDB
  run rows into `analysis/dashboard_template.html` at the `__AGENTVIZ_DATA__` placeholder
  (vanilla JS + inline SVG, no server). **`RUN_COLUMNS` (build_dashboard.py:33-42) is the
  Parquet→template contract.** `analysis/queries.py` has the DuckDB helpers (`connect`,
  `summary_by`, `concurrency_summary`).
  - **The mockup `mcp/agent_dashboard_sample_v2.html` and `analysis/dashboard_template.html`
    are structurally the same artifact** (identical section IDs); the mockup is just the
    template filled with 108 fake runs. "Fold mockup into generator" = port HTML/JS diffs
    into the template + add new per-run fields to `RUN_COLUMNS`.
- **`mcp/gold_metrics.csv` already has a `field_type` column** (raw_string/extracted_string/
  list), generated by `mcp/generate_gold_metrics.py`. This is the gold label for the new
  type-routing accuracy — no regeneration needed.

## Decisions locked

| Area | Decision |
|---|---|
| Tool consolidation | Replace the 7 metric tools with **3 composite type-tools**: `evaluate_raw_string`, `evaluate_extracted_string`, `evaluate_list`, each running the full per-type composite internally. The 7 metric functions become private helpers. |
| Agent autonomy | Agent **still infers the field type from data shape** (type is NOT handed to it). `selection_accuracy` now grades "routed to the correct type-tool". |
| Reasoning view | **LLM-generated summary per top tool-call path** (requires persisting per-run reasoning first — it's two pieces). |
| GPU type | Capture via **SLURM env var / `nvidia-smi --query-gpu=name`**, thread to the eval run, write per Parquet row. |
| Prompts | Show the **agent system + user prompts, embedded at build time**, keyed by prompt version; add a small **prompt registry** so historical runs render their actual text. |
| Framework | **New explicit `framework`/`serving_engine` field** in backend config → sink → new group-by/filter axis. |
| Glossary | Static definitions panel (free). |
| Runs table | Shrink + scroll (`max-height` + `overflow:auto`) (free). |
| Temperature | Flatten existing `completion_kwargs["temperature"]` into the row (null for reasoning-effort backends like gpt-5-mini). |
| **Parallel local models** | **Migrate to `AsyncOpenAI`** (Decision B) — see Part 6. |

## Part 6 — True parallel execution for local models (Decision B: AsyncOpenAI)

**Confirmed bug:** `--concurrency` does NOT parallelize LLM calls. `runner.py:136` fans out
with `asyncio.Semaphore` + `asyncio.gather`, but the model call is a **synchronous** client
(`config.py:107` builds `OpenAI(...)`) invoked **blocking** inside the coroutine
(`agent.py:240`: `response = llm_step(messages)`, where `llm_step` at agent.py:177-184 is a
sync function). A blocking sync call never yields the event loop, so concurrent runs
serialize at the LLM layer — only one request reaches the model server at a time. This caps
local-model throughput and makes the sequential-vs-parallel GPU study unobservable
(`requests_running` stays ~1).

**Fix — migrate to `AsyncOpenAI` (chosen):**

1. `eval/config.py`: build `AsyncOpenAI(...)` instead of `OpenAI(...)` in `build_backend`
   (config.py:107; import at config.py:15).
2. `eval/agent.py`: make `llm_step` a coroutine — `async def llm_step` and
   `return await client.chat.completions.create(...)` (agent.py:177-184); update the call
   site to `response = await llm_step(messages)` (agent.py:240).
3. Wrappers: `@op` (Weave) supports async; `tenacity @retry` supports coroutine functions —
   verify both still apply cleanly to the async `llm_step` (`_retry_policy` in agent.py).
4. Tests: update `eval/tests/` fakes so the fake client's `chat.completions.create` is
   awaitable (e.g. an async method / `AsyncMock`). Check `test_agent.py`, `conftest.py`.

**Server layer (per framework — pairs with Part 3 `framework`):** the engine must accept
concurrency. vLLM/NIM continuous-batch natively; **Ollama serializes unless
`OLLAMA_NUM_PARALLEL`** is set on the server — configure in the launch/SLURM script per
framework.

**Verify:** run `--concurrency 4` against a local backend; confirm the scraped
`requests_running_end` rises above 1 and batch wall-time drops vs `--concurrency 1`.
